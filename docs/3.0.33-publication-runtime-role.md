# Private publication runtime authority (3.0.33)

This is a disposable PostgreSQL acceptance contract, not a registered migration,
deployed grant set, public capability, or approval to enable publication.
The existing draft version is unchanged.

## Executable scope

`scripts/qa-publication-runtime-role.ts` installs the real schema and private
journal in an owned loopback cluster, then opens a **new connection authenticated
as a LOGIN role** with no superuser, role creation, database creation, inheritance
or BYPASSRLS. It does not use SET ROLE on an administrator session. RESET ROLE
cannot elevate it and SET ROLE to the fixture administrator is rejected.

The actual ResumeStore issue/CAS, ResumeBindings, ResumeOperationGate,
ResumeMessageWriter and ResumePublication execute through that restricted pool:
keyed insert/retry, full snapshot and exact snapshot ACK, later commit,
claim and exact batch ACK. The runtime does not own schema/tables or have schema
CREATE, message UPDATE/DELETE/TRUNCATE, journal UPDATE/DELETE/TRUNCATE, room
deletion/policy mutation, trigger-disabling, or delivery-deletion authority.

The room SHARE lock requires UPDATE privilege on at least one room column.
The fixture grants only last_active_at, not auth_version or room identity.
Subscriber admission similarly needs UPDATE(id) on its single lock row.
Session and receipt mutations remain trusted server-owned SQL, not user SQL.

The pool pins search_path to pg_catalog, the trusted application schema, then
pg_temp. Temporary shadow relations are deliberately created for the journal
and deliveries; both remain empty while actual publication succeeds. The
trigger's existing schema-qualified write is separately necessary: fixing only
the trigger does not pin every unqualified subscriber query. No application
pool is changed by this fixture.

## UPDATE / DELETE decision for this candidate

The present journal is append-only publication, **not a changefeed**. Existing
ACKs have no content revision. A privileged edit to an ACKed message does not
create an unACKed event. Deleting a message cascades away pending/delivery rows;
the existing resume write receipt becomes NULL to prevent recreation, but that
is **not a browser deletion tombstone**. The fixture reproduces both facts in an
administrator transaction and rolls it back, leaving the original message intact.

Therefore no public activation may claim mutation propagation. Runtime message
and global-journal UPDATE/DELETE/TRUNCATE must be denied and verified under the
actual deployed login. Privileged retention, deletion, migrations or repair
must not run concurrently with this protocol without an explicit fencing and
client invalidation contract or versioned durable tombstones. This does not
remove the separate retention design in PR6 or silently select infinite
retention as a product policy.

## Remaining deployment gates

This proof establishes feasibility, not the deployed least-privilege policy.
The invoker trigger still needs journal INSERT; the application role can execute
direct inserts. Subscriber/session UPDATE is server-wide, not SQL row-level
tenant isolation. Credential holders, schema/function ownership, PUBLIC and
inherited grants, default privileges and startup migration roles still need
release-specific audit. This fixture grants SELECT on its owned tables only;
it is not a production GRANT script.

All producers under the final deployed role, restricted full-server startup,
session cleanup role separation, consistent permanent-schema pool settings,
sustainable message/journal/receipt admission and expiry, public authenticated
rendered resume/reload and actual file bytes remain required. A 256-row browser
cap does not bound total database growth; append-only denial does not solve
capacity. Physical byte/inode authority and fresh OLD-writer-fenced paired
backup/exact NEW-image rollout gates remain unchanged. No live data or grants
are changed by this acceptance.

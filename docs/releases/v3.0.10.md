# Dimle 3.0.10 — bounded multipart upload parsing

Focused security fix for issue #21, independent of draft resume PR #20.
Pins Multer 2.4.0 and matching v2 types. The existing admitted/rate-limited
upload route accepts one file and zero text fields, with one multipart part.
Rejecting fields before append-field prevents the locally reproduced sparse
array/key CPU denial of service. Upgrading Multer alone did NOT fix that probe.
Room/socket admission, rate limits, file naming and persistence are unchanged.
Destination mkdir errors now reach the middleware callback instead of throwing.

Multer 2.4's file-size and part bounds are inclusive: a file exactly at the
configured maximum is now accepted; max+1 is rejected. Twelve real loopback HTTP
and disk tests cover normal/exact/oversize uploads, malicious fields, extra
files, malformed/truncated bodies, sink failure, and disconnect cleanup with
one callback. This does not claim disk quotas, empty-directory cleanup, bounded
whole-request time, a verified header-count bound, or the unfinished resume API.

CI must additionally verify the full PostgreSQL/Socket.IO application harness,
including rejection without file broadcast and continued socket operation.
No database migrations or listener changes. No production or staging deployment
is included. Production requires Max's fresh approval and the release/recovery
audit; existing backup and migration gates remain open.

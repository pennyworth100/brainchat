# Private atomic message admission (3.0.33)

`scripts/fixtures/message-write-admission.sql` adds a **private prototype** for
bounding committed message population and its UTF8 JSON-envelope bytes. The
global publication journal has one entry per message. This is not a registered
migration, deployed quota, retention policy, physical allocation guarantee, or
proof of sustainable operation. No product capability is activated.

## Contract and authority

Installation locks message writers and backfills one singleton counter in the
same transaction as trigger creation. Limits initially equal the existing
population: new inserts are closed until a trusted administrator chooses an
explicit budget. There is no guessed production limit. The singleton UPDATE
serializes admissions and checks both remaining rows and bytes atomically.
The AFTER INSERT trigger does not charge `ON CONFLICT DO NOTHING`; charge,
message and journal all settle in one transaction. Missing/exhausted budget
raises SQLSTATE 53100. A lost response is not deletion/refund authority.

Runtime is an actual restricted LOGIN, not SET ROLE on an admin connection.
It cannot read/mutate the budget, execute the definer function directly,
disable triggers, update messages or delete history. Only the trigger can use
the trusted installer's authority. The function pins `pg_catalog, pg_temp`
and schema-qualifies its counter using the trigger table's schema; temporary
objects cannot replace it. PUBLIC has no counter/function privilege. The
installer and schema owner must remain trusted; this is not a defense against
administrators, replication bypass or owner DDL. Production owner/default
grants and pool integration still require a separate audit.

The budget is intentionally monotone. No delete/expiry/ACK automatically returns
message capacity. Privileged deletes would leave conservative accounting, not
authorize a refund. Privileged updates could invalidate byte accounting and
remain outside this append-only contract. Ordinary retries still need the
existing writer's payload-identity validation; raw ON CONFLICT is not that proof.

## Executable acceptance

`qa-message-write-admission.ts` runs in a dedicated schema of the owned
PostgreSQL fixture and is included in the existing PG16/18 CI job. It checks:

- Exact installation backfill, initially closed writes, and non-charging retry.
- Actual restricted login, forbidden counter/history/trigger/function actions,
  and a temporary counter shadow that cannot bypass the real limit.
- Byte exhaustion independently of row exhaustion, including UTF8 content.
- Transaction rollback and later journal failure refunding the entire charge.
- A real competing connection blocked on the final slot: after the first
  commit the competitor fails, rather than overshooting the limit.
- Multi-row statement rollback when only its first row fits; no partial message,
  journal or counter persistence.
- Exact committed count/bytes and missing-counter fail-closed behavior.
- Immediate PostgreSQL stop/start and a NEW Node process: counters persist,
  exhausted writes stay closed and an existing keyed retry still costs nothing.

## Remaining gates

This bounds **committed logical data only**. A rejected AFTER INSERT can already
have performed physical writes; rollback/failed retries can generate dead
tuples, sequence consumption and WAL. Indexes, TOAST, journal overhead, temporary
files, bloat, vacuum, transaction work and in-flight payload memory are not
bounded by these counters. Physical byte/inode authority remains a separate
provider/storage gate. The global singleton is a contention point; production
statement/lock deadlines and safe error responses remain required.

No retention, receipt pruning or cascade scheduler was added. Runtime messages
and the global journal remain append-only; full capacity means fail-closed, not
silent history loss. Sustainable maintenance needs bounded receipt/cascade work,
explicit cadence and safe admission/reclamation policy. Real public producer
integration/error handling, role/pool deployment, browser resume/reload and file
bytes, and fresh fenced paired backup/exact-image release checks remain open.

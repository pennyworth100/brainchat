# Private durable publication boundary — first executable slice

This SQL prototype is deliberately NOT a Drizzle migration and is NOT loaded by
server startup. No public activation, version change or deployment.

## Producer inventory

All current room-persistence paths insert into the same messages table:
server.ts saveMessage (including unkeyed agent HTTP), keyed saveAgentMessage
(ON CONFLICT retry), transactional legacy file upload, ResumeMessageWriter
(including insertResumeTextMessage), ResumeImageWriter and ResumeFileWriter.
A database AFTER INSERT trigger covers their persistence boundary without
depending on each handler reaching broadcast, touchRoom or a finalizer.
DMs use separate authority and are NOT covered or authorized by this proposal.

The fixture tests these SQL families and composes the journal with the actual
ResumeMessageWriter, ResumeImageWriter and ResumeFileWriter regression suite,
including retry/rollback and private browser fixtures. It does NOT invoke every
real public HTTP/socket producer; public browser/media acceptance remains open.

## Proven / deliberately unproven

Install plus old-message backfill take one transaction and a table writer lock.
Message and pending record commit or roll back together; a failed enqueue fails
the message transaction. Idempotent non-inserts do not enqueue duplicates.
Pending work is a set, not an afterId/MAX(id) watermark. A lower-ID late commit,
fanout exception and a message displaced from newest100 stay discoverable.
An actual immediate PostgreSQL stop/start plus a NEW Node process proves pending
records survive recovery. This is not network delivery or exactly-once proof.

The private ResumePublication prototype now keeps a durable per-session ACK set,
with authenticated room/session/generation/physical-incarnation validation under
ResumeOperationGate. Each claim has a new deliveryTry and a five-second lease.
Socket.IO client ACK (four-second deadline), not emit, completes that subscriber's
delivery. Expired attempts redeliver; a successor generation fences old attempts.
No ACK deletes the shared journal or consumes another subscriber's message.
The receiver fixture explicitly deduplicates message IDs (at-least-once only).

Registration and first bounded pending-set read share one authorized transaction.
Later/lower-ID commits remain discoverable through the journal on future polls.
This is NOT yet the public browser's atomic full snapshot/subscription protocol:
no READY assertion, UI/page registration, automatic poll loop, or migration.
The existing two-read snapshot handoff remains insufficient.

Bounds: 100 retained subscribers, 256 retained per-subscriber receipts, 16 messages
and 1MiB serialized message rows per claim, 32 concurrent socket reconciliations,
one flight per physical socket. Exceeding limits rejects/rolls back; it does not
evict live ACK state. Subscription expiry is fixed to the authenticated session;
existing session deletion cascades, but sustainable retention/admission is OPEN.
The shared journal remains unbounded. SQL scan cost and database byte allocation
are NOT bounded by result limits. Hung DB work retains capacity until settlement.

The owned PostgreSQL/Socket.IO fixture composes the actual ResumeMessageWriter
with dropped ACK/redelivery, two independent subscribers, wrong physical owners,
copied/stale bindings, late lower-ID commit, lease-token replay, disconnect,
successor transfer, expiry, byte/receipt exhaustion and real immediate database
restart. A NEW Node process uses the retained TEST credential through the actual
bearer CAS and physical owner, receives only its unACKed message and ACKs it.
The TEST credential exists only in the disposable database, never output.
Actual private image/file writer composition remains covered by the existing
writer suite, NOT by rendered browser reception or authenticated file-byte tests.

Physical byte/inode and database growth/admission gates remain open. A full
backfill/table lock needs release-specific sizing and recovery review; no
permission to apply this prototype to a live database. UPDATE/DELETE/tombstone
semantics and role/search_path hardening are still to be designed before a
registered migration. Do not mark PR44 ready on this fixture alone.

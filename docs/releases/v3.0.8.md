# Dimle 3.0.8 — migration-aware deployment readiness

Adds a source-controlled Railway startup HTTP healthcheck: unauthenticated
`GET /`, with a finite 300-second deployment health deadline. The existing
server awaits database migrations and Next preparation before listening, so
this route cannot return 200 while startup migration is blocked. No new public
endpoint, dependency, migration or application database query is introduced.

300 seconds is an explicit initial rollout budget, not a measured production
migration duration or a PostgreSQL lock/statement timeout. A live process that
is waiting on a database lock is not ready. If the deadline expires, investigate
the deployment and blocker; do not promote on process liveness alone or
automatically kill production transactions. Do not assume schema rollback.

Railway's deployment healthcheck is not continuous database monitoring. After
startup, GET / does not prove current DB availability. This change alone does
not prove zero downtime, backup restoration or listener exactly-once behavior.

## Rollout gate

Merging this configuration is not a deployment. Do not replace the held 3.0.5
staging listener baseline until a separate test window is authorized. At the
next permitted staging deployment, verify that the effective deploy manifest
contains healthcheckPath=/ and healthcheckTimeout=300 and that Railway waits
for HTTP 200. Local probe evidence cannot attest platform enforcement.

Before production, check current DB size, long transactions, backup/restore
readiness and the suitability of the 300-second budget; record a short audit
and obtain fresh explicit Max approval. Listener restart, new candy986 test
messages and physical BRA-11 remain separately on HOLD. For rollback to 3.0.3,
first quiesce 3.0.5+ consumers, preserve additive schema and avoid uncertain
write replay through the old API, which ignores clientMessageId.

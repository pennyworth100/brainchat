# 3.0.34 — bounded public draft and uncertain-operation retention

Status: DRAFT, stacked on PR44; not release or managed-candidate acceptance.

## Public path
RoomInner restores only after successful room authentication, under a key containing
a random tab-owner token, normalized room ID and exact username. The token is in
sessionStorage; no password, creation token or bearer authority is persisted.
Drafts are synchronously written/read back through localStorage (32,768 code units),
with a new random revision per edit (including identical-text edits). Version-one
plain drafts remain readable until the first version-two envelope is written.
Files (native File, including bytes/name/type) and text operations are committed to
IndexedDB with strict transaction durability BEFORE calling the transport.
clientMessageId and conservative UNKNOWN state are stored with the exact payload.

One unresolved operation blocks further sends for that scope, including explicit
attempts with changed content. No auto replay, replacement identity, silent eviction,
or new legacy fallback. The store admits at most 8 operations and 100 MiB of logical
payload globally, checked in the same readwrite transaction as reservation.
Storage denied, unavailable, blocked, quota failure, and failed transaction do not
authorize dispatch. An acknowledged operation is deleted only under its exact ID
after the existing owner fence and a validated receipt. The exact operation is first
marked CONFIRMED with its validated server message ID in a strict IDB transaction.
For text, its pre-dispatch draft revision is then conditionally cleared, and only
then is the operation deleted. A confirmed tombstone survives either cleanup failure.
On authenticated same-owner reload, cleanup resumes without any transport replay.
Newer edits, even with identical text, survive. Other owners cannot settle the row.
Live UI distinguishes confirmed-but-unfinished cleanup from UNKNOWN delivery.
A failed preflight releases its exact reservation only if the transport dispatch
boundary was never crossed. Both text and file transports mark that boundary
synchronously before their first emit/request. Thrown fetch, lost ACK, server errors,
and later reauthentication failures remain UNKNOWN once the boundary was crossed.
Cleanup failure keeps the record blocked; it never authorizes automatic retry.
The saved draft is not cleared by known-unsent cleanup, and any new attempt is explicit.

This is NOT an upgrade of the existing legacy public server to resume authority.
Legacy uploads still have no server-side operation-key receipt; their saved ID is
local identity only. Strict uploads use the retained ID in the existing strict
protocol, without downgrade. Neither lane gains permission to replay UNKNOWN.
Legacy success receipts now also require matching file name/size and valid message
identity before the browser settles its retained operation.

## Evidence
- Built public React UI with a loopback controlled Socket.IO/HTTP fixture:
  draft + unknown file restored after reload/reauthentication, exact file bytes and
  original ID retained, no replay; duplicate send blocked; another username sees
  neither draft nor uncertainty; lost text ACK retains its payload and original ID;
  denied IndexedDB and quota failure dispatch no upload; no uncaught page errors.
- Unit/regression suite, explicit typecheck, production build and production audit.
- 14 built-UI loopback scenarios now include failures before draft clearing and
  before receipt deletion, same-owner reload without replay, wrong-owner isolation,
  identical newer persisted/unsaved edits, and failed confirmation persistence
  retaining UNKNOWN. Three unit tests cover revision identity and legacy migration.
- The browser fixture is in CI. It uses a controlled protocol and no database;
  do not report it as managed Railway/database or physical iPhone acceptance.

## Remaining release gates / known limits
- Re-run the two previously failing gates on a new managed candidate image, plus
  wrong-owner/storage-denial checks, independently preserving all recovery data.
- Implement reviewed settlement/reconciliation UX for retained UNKNOWN. A lost ACK,
  crash before durable confirmation, or failure to persist that confirmation still
  blocks a scope indefinitely instead of offering unsafe discard/retry. Durable
  CONFIRMED cleanup recovery is not a server receipt lookup for UNKNOWN.
- A tab-owner token is NOT server session authority. New tabs, browser data deletion,
  sessionStorage loss, permanent browser eviction, and full-device failure are not
  restored by this design. Do not claim general crash recovery or cross-device resume.
- Draft and operation stores do not share a transaction. Ordered durable confirmation,
  revision-checked draft clearing, then ID-checked removal provide repeatable local
  reconciliation; this is not an atomic transaction with the server. A browser crash
  after server commit but before local confirmation remains UNKNOWN. Logical fault
  injection and reload tests do not prove physical browser/device power-loss durability.
- Cloned tab tokens, cross-tab concurrent access to one owner scope, browser data
  eviction, and retained credentials across a replaced server session remain outside
  this design. No automatic resend or history-content-based inference was added.
- Draft storage uses per-scope bounds and the browser origin quota; the operation
  byte cap is logical payload, not exact physical browser disk allocation.
- Keep PR44/this patch DRAFT/unmerged until managed acceptance, reconciliation,
  existing admission/expiry/provider-capacity/recovery gates and release audit pass.
Production approval exists; technical gates are not an authorization blocker.

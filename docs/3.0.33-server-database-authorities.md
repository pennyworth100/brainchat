# Private full-server database authority composition

Draft 3.0.33 now accepts caller-owned `databaseAuthorities` in `main`: separate
migration and maintenance pools, alongside the existing runtime pool. All three
pool objects must differ. Migrations use only the migration pool; both rate-limit
and session maintenance use the maintenance pool. `publicationTables: true`
selects bounded publication child cleanup. No CLI/environment toggle, public
capability, migration registration or deployed credentials are introduced.
Default startup remains unchanged. Caller closes supplied pools only after
server lifecycle settlement, including startup failure settlement.

Run the disposable full-server acceptance with
`python3 scripts/qa-public-session-fixture.py --database-authorities` and `PG_BIN`.
It authenticates separate restricted runtime/maintenance LOGINs, pins application
search_path to pg_catalog/public/pg_temp, runs real startup migrations using the
administrator pool, creates a room and authenticated socket membership, proves
one keyed write/retry, and drains 205 expired deliveries through the actual server
scheduler while preserving global messages/journal and the live session.

This is private composition, not a deployed-role attestation: distinct pool objects
alone do NOT establish different SQL identities. Fixture runtime grants remain
broader than a final least-privilege deployment policy. Callers must validate
database/schema identity, role ownership, effective/inherited/default grants and
TLS before deployment. No public publication adapter is enabled; bounded admission,
sustainable expiry, physical BYTE+INODE authority, rendered resume/file bytes and
fresh fenced paired backup/exact release audit remain gates.
